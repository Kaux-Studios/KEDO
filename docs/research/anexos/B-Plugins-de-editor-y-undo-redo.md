# Research B: Godot 4.6 editor plugins (C#), inspector plugins, undo/redo, addons, export hygiene

Target: Godot 4.6.2 .NET, C# 12, .NET 8, Windows. Researched 2026-10-15.
Each claim is tagged **VERIFIED (url)** when read from an official doc page, engine source, or the primary issue/repo, or **INFERRED** when derived from those facts or from secondary/community sources.

Conventions used below: GDScript names are given as in the class reference (`_enter_tree`); the C# names are the PascalCase equivalents (`_EnterTree`, `AddInspectorPlugin`, `EditorInterface.Singleton`).

## 1. EditorPlugin in C#

### 1.1 plugin.cfg, [Tool], build step
- `plugin.cfg` is an INI file with a `[plugin]` section and fields `name`, `description`, `author`, `version`, `script`. `script` may point at a `.cs` file; the editor's "Create New Plugin" dialog has a Language field and generates a C# skeleton. **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/plugins/editor/making_plugins.html)
- The main script must be marked `[Tool]` and inherit `EditorPlugin`; every other script the plugin uses must also be a tool script "or it acts like an empty file". Setup goes in `_EnterTree`, cleanup in `_ExitTree`. **VERIFIED** (same page)
- The official C# examples wrap the whole class in `#if TOOLS` and use `[Tool] public partial class ... : EditorPlugin`. "In C#, the EditorPlugin script needs to be compiled, which requires building the project" before the plugin can be enabled in Project Settings > Plugins. **VERIFIED** (same page; also https://docs.godotengine.org/en/4.6/tutorials/plugins/editor/making_main_screen_plugins.html)
- Class name must match the file name (`Cannot find class XXX for script res://XXX.cs` otherwise). **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_basics.html)
- The 4.6 C# basics page still says: "Writing editor plugins is possible, but it is currently quite convoluted." and "You will also need to rebuild the project assemblies to apply changes in 'tool' scripts." **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_basics.html)
- C# `EditorScript`s need `[GlobalClass]` to appear in the command palette; the script editor's "Run" only works for GDScript. **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/plugins/running_code_in_the_editor.html)

### 1.2 Main screen plugins
- Override `_HasMainScreen() => true`, `_GetPluginName()` (button label; also required for state save/restore), `_GetPluginIcon()` (must return a Texture2D, ideally 16x16 white on transparent), `_MakeVisible(bool)` (show/hide your panel; visibility is your responsibility). **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorplugin.html)
- In `_EnterTree`: instantiate the panel scene and add it as a child of `EditorInterface.Singleton.GetEditorMainScreen()`, then call `_MakeVisible(false)` so it does not take space on load. In `_ExitTree`: `QueueFree()` the panel. Null-check the panel in `_MakeVisible` and `_ExitTree`. The C# version uses `ResourceLoader.Load<PackedScene>` and `EditorInterface.Singleton` for theme/icon. **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/plugins/editor/making_main_screen_plugins.html)
- `GetEditorMainScreen()` returns a `VBoxContainer`; children need vertical size flags expand+fill. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorinterface.html)
- `EditorInterface.SetMainScreenEditor(name)` switches tabs; the name must exactly match the tab title (e.g. "2D", "Script", or your `_GetPluginName()`). `EditorPlugin.MainScreenChanged(screen_name)` signal fires on workspace change, including custom screens. **VERIFIED** (class_editorinterface.html, class_editorplugin.html)
- `_Handles(object)` / `_Edit(object)` are optional; `_Handles` returning true makes the editor call `_Edit` and `_MakeVisible` when a matching object is selected, so selecting a GDO `.tres` in the FileSystem dock could jump to the Contenido screen. **VERIFIED** (class_editorplugin.html)

### 1.3 Docks (4.6 API)
- 4.6 introduces `EditorDock` (experimental: "may be changed or removed in future versions") and `EditorPlugin.add_dock(dock)` / `remove_dock(dock)`. `add_control_to_dock(slot, control, shortcut)` is marked **Deprecated** in the 4.6 class reference: "use add_dock() instead". The 4.6 "Making plugins" tutorial already uses `EditorDock` with `default_slot = DockSlot.LeftUl`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorplugin.html, https://docs.godotengine.org/en/4.6/classes/class_editordock.html, making_plugins.html)
- `EditorDock` properties: `title`, `dock_icon` / `icon_name` (EditorIcons theme name), `default_slot` (DockSlot enum; LEFT_UL..RIGHT_BR, BOTTOM=8), `available_layouts` (bitmask VERTICAL=1, HORIZONTAL=2 (bottom panel), FLOATING=4; default 5 = vertical+floating), `closable`, `global`, `layout_key`, `transient`, `dock_shortcut`. Methods `open()`, `close()`, `make_visible()`; virtuals `_save_layout_to_config` / `_load_layout_from_config`. The editor remembers slot moves between sessions. **VERIFIED** (class_editordock.html)
- The 4.6 release unified the dock system: bottom panels are now regular docks, docks can be dragged between sides and bottom and floated. **VERIFIED** (https://godotengine.org/releases/4.6/)
- `add_control_to_bottom_panel` is likewise deprecated in favour of `add_dock` with `default_slot = DOCK_SLOT_BOTTOM`. **INFERRED** (seen only in commit-mirror diffs of the "Rework editor docks" change; the 4.6 class page excerpt I read did not show that marker explicitly).
- `add_control_to_container(container, control)` remains for predefined editor locations (toolbars etc.). **VERIFIED** (class_editorplugin.html)
- The 4.6 upgrade guide lists no breaking changes for EditorPlugin/EditorDock; it does list `EditorFileDialog` changes (see 2.5). **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/migrating/upgrading_to_godot_4.6.html)

### 1.4 Unsaved status, external data, apply changes, build hook
- `_GetUnsavedStatus(string forScene) -> string`: return a message describing unsaved changes or "" when none. `forScene` is the path of the scene being closed; it is empty when the editor is exiting. **VERIFIED** (class_editorplugin.html)
- `_SaveExternalData()`: "called after the editor saves the project or when it's closed", meant to save the plugin's own external scenes/resources. **VERIFIED** (class_editorplugin.html)
- `_ApplyChanges()`: asks the plugin to apply pending edits, e.g. before saving or switching tabs. `_Clear()` resets plugin state. **VERIFIED** (class_editorplugin.html)
- `_Build() -> bool`: runs before the project starts; returning false aborts the run (useful to block Play while GDO validation has errors). **VERIFIED** (class_editorplugin.html)
- Engine behaviour read from `editor/editor_node.cpp` (branch 4.6):
  - `EditorNode::_save_external_resources(bool p_also_save_external_data)`: walks `ResourceCache::get_cached_resources`, skips resources where `!res->is_edited()`, takes those whose path starts with `res://` (stripping any `::` subresource suffix), calls `res->set_edited(false)` and `ResourceSaver::save(res, res->get_path(), flg)` (PackedScenes skipped). With `p_also_save_external_data` true it loops over plugins and calls `plugin->save_external_data()` for every plugin whose `get_unsaved_status()` is non-empty. It then marks the global undo history as saved and calls `_update_unsaved_cache()`. It is called from `_save_scene` (so Ctrl+S on any scene also flushes edited external `.tres` files). **VERIFIED** (https://raw.githubusercontent.com/godotengine/godot/4.6/editor/editor_node.cpp)
  - `_save_all_scenes()` only iterates scenes with `_is_scene_unsaved(i)` and calls `_save_scene` / `_save_scene_with_preview` for them; it does not call `_save_external_resources` itself. So `EditorInterface.SaveAllScenes()` flushes edited external resources only as a side effect of saving at least one unsaved scene. If no scene is dirty, nothing is written. **VERIFIED** (same file, chunk 100k-200k) — practical consequence for a resource-only tool: call `ResourceSaver.Save` yourself. **INFERRED**
  - Quit flow (`_menu_option_confirm`, case `SCENE_QUIT`): if no unsaved scenes, it checks `is_history_unsaved(GLOBAL_HISTORY)` and shows "Save modified resources before closing?"; otherwise it loops plugins and the first non-empty `get_unsaved_status()` becomes the dialog text and that plugin is stored in `plugin_to_save`; on confirm it calls `plugin_to_save->save_external_data()`, then `_save_external_resources(); _discard_changes();`. Closing a scene tab (`_scene_tab_closed`) does the same per-scene check and calls `get_unsaved_status(scene_filename)` on each plugin, showing "Save & Close". **VERIFIED** (same file)
  - `_update_unsaved_cache` is connected to `EditorUndoRedoManager` `version_changed` and `history_changed`. **VERIFIED** (same file, chunk 300k+)
  - Known wart: in `_save_external_data` the plugin may already be out of the tree and it can be called twice on "Save & Quit" and once even on "Don't Save"; guard with `IsInsideTree()` and your own dirty flag. **VERIFIED** (comment devvosaur Apr 2024 in https://github.com/godotengine/godot-proposals/discussions/7168)

### 1.5 Filesystem scanning and listing resources by type
- `EditorInterface.GetResourceFilesystem()` returns the `EditorFileSystem` singleton (do not instantiate). Methods: `get_filesystem()` (root `EditorFileSystemDirectory`), `get_filesystem_path(path)`, `get_file_type(path)` (returns a type name such as "Resource" or "GDScript", not an extension), `scan()`, `scan_sources()`, `update_file(path)` (register a file written by an external program; does not import), `reimport_files(files)` (blocks but keeps the main loop running), `is_scanning()`, `get_scanning_progress()`. Signals: `filesystem_changed`, `script_classes_updated`, `sources_changed(exist)`, `resources_reimported`, `resources_reimporting`, `resources_reload`. Avoid calling `scan()`/`reimport_files()` during an import. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorfilesystem.html)
- `EditorFileSystemDirectory`: `get_file_count()`, `get_file(idx)`, `get_file_path(idx)`, `get_file_type(idx)` (engine type, e.g. "Resource"), `get_file_script_class_name(idx)` (script global class name or ""), `get_file_script_class_extends(idx)`, `get_file_import_is_valid(idx)`, `get_subdir_count()`, `get_subdir(idx)`, `get_parent()`, `find_file_index(name)`, `find_dir_index(name)`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorfilesystemdirectory.html)
- In `editor_file_system.cpp` the per-file `type` comes from `ResourceLoader::get_resource_type(path)` and `resource_script_class` from `ResourceLoader::get_resource_script_class(path)`; both are cached in the filesystem cache as `type/script_class`. **VERIFIED** (https://raw.githubusercontent.com/godotengine/godot/4.6/editor/file_system/editor_file_system.cpp)
- Consequence: for a `.tres` whose script is a C# `[GlobalClass] partial class Campaign : Resource`, expect `get_file_type` == "Resource" and `get_file_script_class_name` == "Campaign" (the `.tres` header stores `script_class="Campaign"` when the script has a global class name). Recursively walking the directory tree and filtering on `get_file_script_class_name` (plus `get_file_script_class_extends` for family hierarchies) is the cheap way to list GDOs without loading every resource. **INFERRED** (from the source above plus the `.tres` header format; verify once on a real file; if the C# class lacks `[GlobalClass]`, the script-class name will be empty and you must load the file to know its type).
- Alternative to writing your own picker: `EditorInterface.PopupQuickOpen(callback, baseTypes)` opens the editor's quick-open filtered by base types; `PopupNodeSelector`, `PopupPropertySelector` exist too. **VERIFIED** (class_editorinterface.html)
- Previews: `EditorInterface.GetResourcePreviewer()` returns `EditorResourcePreview` for texture/scene thumbnails in your lists. **VERIFIED** (class_editorinterface.html)

### 1.6 EditResource / InspectObject / selection
- `EditorInterface.EditResource(resource)` opens a resource in the Inspector; `EditNode(node)`; `InspectObject(object, forProperty = "", inspectorOnly = false)` shows an object in the Inspector, and with `inspectorOnly` true plugins will not `_Edit` it. `GetInspector()` returns the `EditorInspector`; `GetSelection()` the `EditorSelection`; `GetBaseControl()` the editor root control (never free it); `GetEditorTheme()`; `GetEditorScale()` for sizing; `PopupDialog(window, rect)` for exclusive dialogs (window must have no parent). **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorinterface.html)
- `EditorPlugin` signals: `resource_saved(resource)`, `scene_saved(path)`, `scene_changed(root)`, `scene_closed(path)`, `main_screen_changed(name)`; `project_settings_changed` is deprecated (use `ProjectSettings.settings_changed`). **VERIFIED** (class_editorplugin.html)
- `add_tool_menu_item(name, callable)` / `add_tool_submenu_item(name, popup)` put entries under Project > Tools. **VERIFIED** (class_editorplugin.html)

## 2. EditorInspectorPlugin, EditorProperty, dynamic properties, pickers, file dialogs

### 2.1 EditorInspectorPlugin
- Lifecycle: when the Inspector opens an object it calls `_can_handle(object)`; if true, `_parse_begin(object)`, then `_parse_category(object, category)`, `_parse_group(object, group)` and `_parse_property(...)` per item, finally `_parse_end(object)`. `_can_handle` also covers any Resource attached to the object (sub-inspectors). Register with `EditorPlugin.AddInspectorPlugin(plugin)` in `_EnterTree` and `RemoveInspectorPlugin` in `_ExitTree`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorinspectorplugin.html, https://docs.godotengine.org/en/4.6/tutorials/plugins/editor/inspector_plugins.html)
- `bool _parse_property(Object object, Variant.Type type, string name, PropertyHint hintType, string hintString, BitField<PropertyUsageFlags> usageFlags, bool wide)`: return `true` to remove the built-in editor for that property; return `false` to keep it (custom editors added in the call are inserted before the built-in one). **VERIFIED** (class_editorinspectorplugin.html)
- `add_custom_control(control)` (any Control), `add_property_editor(property, editor, add_to_end = false, label = "")` — the `label` argument is how you give a property a friendly display name; empty label means "generated from the property name". `add_property_editor_for_multiple_properties(label, properties, editor)` edits several at once. The editor must extend `EditorProperty`. **VERIFIED** (class_editorinspectorplugin.html)
- Hiding a property: the only inspector-plugin way is to return `true` from `_parse_property` without adding an editor. Renaming: via the `label` parameter above (you still add a custom EditorProperty) or by wrapping the stock editor logic yourself. **INFERRED** (from the API surface; there is no "rename only" hook).
- The official tutorial includes a complete C# version (`[Tool]` plugin in `#if TOOLS`, `MyInspectorPlugin : EditorInspectorPlugin` overriding `_CanHandle`/`_ParseProperty`, `RandomIntEditor : EditorProperty` using `AddChild`, `AddFocusable`, `EmitChanged(GetEditedProperty(), value)`, `_UpdateProperty` reading `(int)GetEditedObject().Get(GetEditedProperty())`). **VERIFIED** (inspector_plugins.html)

### 2.2 EditorProperty (custom property controls)
- Properties: `label`, `read_only`, `checkable`/`checked`, `draw_warning`, `keying`, `deletable`, `name_split_ratio` (0.5), `selectable`, `use_folding`, `draw_label`, `draw_background`. Methods: `_update_property()` (refresh UI from the object; `get_edited_object()`/`get_edited_property()` are non-null here), `_set_read_only(bool)`, `emit_changed(property, value, field = "", changing = false)` (never emit `property_changed` manually), `add_focusable(control)` (keeps focus across inspector refresh), `set_bottom_editor(control)` (control below the label), `update_property()`. Signals of note: `property_changed`, `resource_selected(path, resource)` (request editing a sub-resource), `property_pinned`, `property_favorited`, `property_can_revert_changed`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorproperty.html)
- Layout rule from the tutorial: `add_child()` puts the control right of the name; `add_child()` + `set_bottom_editor()` puts it under the name. Use an `updating` guard flag to avoid feedback loops in `_update_property`. **VERIFIED** (inspector_plugins.html)
- Changes emitted via `emit_changed` go through the Inspector, which commits them to the `EditorUndoRedoManager`, so custom property editors get undo/redo for free. **INFERRED** (standard Inspector behaviour; the tutorial does not spell it out).

### 2.3 Property metadata: `_ValidateProperty`, `_GetPropertyList`, groups, labels, help
- `_validate_property(Dictionary property)`: override to customize existing properties; every property passes through it except those added by `_get_property_list()`. The dict has `name`, `class_name`, `type`, `hint`, `hint_string`, `usage`. The doc example makes a property read-only by OR-ing `PropertyUsageFlags.ReadOnly` into `property["usage"]` (C# example exists). Hiding: remove `PROPERTY_USAGE_EDITOR` from `usage` (keep `STORAGE`). **VERIFIED** for the mechanism and the ReadOnly example (https://docs.godotengine.org/en/4.6/classes/class_object.html); **INFERRED** for the "clear EDITOR flag to hide" recipe (standard usage of the flags).
- `_get_property_list()` returns extra property dicts (must contain at least `name` and `type`); `_get`/`_set` handle them (not called for built-in/exported properties); `_property_can_revert`/`_property_get_revert` drive the revert arrow; `notify_property_list_changed()` refreshes the Inspector after the list changes. Non-tool scripts' overrides are not called in the editor. **VERIFIED** (class_object.html; https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_exports.html says the script must be a tool for these to work in-editor)
- Grouping in C#: `[ExportGroup("Name", "prefix_")]`, `[ExportSubgroup]`, `[ExportCategory]` (categories break the inheritance-ordered list, use sparingly). Enum members `Thing1`, `AnotherThing` show as "Thing 1", "Another Thing" (name beautification). **VERIFIED** (c_sharp_exports.html)
- Inspector label derivation: property names are "beautified" (capitalized, separated) automatically; there is no attribute to set a custom label on an `[Export]` member. **INFERRED** (the docs show the effect but not the rule).
- Help/tooltips for C# exported properties: a third-party post claims `/// <summary>` XML doc comments appear as Inspector tooltips when `GenerateDocumentationFile` is enabled in the `.csproj`. Not confirmed by official docs; test it on 4.6.2 before relying on it. **INFERRED** (https://bugnet.io/blog/fix-godot-csharp-export-property-tooltip-not-shown)
- In tool scripts, changing a Resource's property from the Inspector does not call your C# setter's side effects reliably; the official advice is to make the resource a tool, call `EmitChanged()`/emit `changed`, and connect to it. **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/plugins/running_code_in_the_editor.html)

### 2.4 EditorResourcePicker
- `EditorResourcePicker : HBoxContainer` is the Inspector's resource field, explicitly intended for reuse with `EditorInspectorPlugin`. Properties: `base_type` (comma-separated list of allowed types), `edited_resource`, `editable`, `toggle_mode`. Methods: `get_allowed_types()`, `set_toggle_pressed()`, virtuals `_set_create_options(menu_node)` (replace the "New ..." items) and `_handle_menu_selected(id)`. Signals: `resource_changed(resource)`, `resource_selected(resource, inspect)`. It does not edit the resource itself. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorresourcepicker.html)
- Drag-and-drop (from `editor/inspector/editor_resource_picker.cpp`, 4.6): implemented via `can_drop_data_fw` / `drop_data_fw` forwarded from the assign button. Accepts drag data of type `"resource"`, `"files"` (exactly one path; validated with `ResourceLoader::exists` + load to check type) and `"script_list_element"`. Type check: `base_type` entries are expanded to engine subclasses (`ClassDB::get_inheriters_from_class`) and script subclasses (`ScriptServer::get_inheriters_list`), names not in ClassDB are treated as script classes; `_is_type_valid` matches exact name, `ClassDB::is_parent_class`, or `script_class_is_parent`; `_get_resource_type` returns the script's global class name when present. Conversions on drop: `Texture2D -> BaseMaterial3D` albedo, `Shader -> ShaderMaterial`, `Image -> ImageTexture`. Ctrl while dropping makes the dropped resource unique. Empty `base_type` accepts anything. **VERIFIED** (https://raw.githubusercontent.com/godotengine/godot/4.6/editor/inspector/editor_resource_picker.cpp)
- Context menu: Load... (EditorFileDialog filtered by extensions of the base types), Quick Load..., Edit/Inspect, Clear, Make Unique, Make Unique (Recursive), Save, Save As..., Copy, Paste, Paste as Unique (4.5+), Show in FileSystem, Convert To..., plus "New <Type>" for allowed types. **VERIFIED** (same source; "Paste as Unique" also in https://godotengine.org/releases/4.5/)
- So a picker with `BaseType = "Texture2D"` or `"AudioStream"` gives drag-from-FileSystem-dock, Load, Quick Load and previews for free, and `BaseType = "Campaign,Actor"` works for C# `[GlobalClass]` resources. **INFERRED** (direct consequence of the source above).

### 2.5 EditorFileDialog
- `EditorFileDialog` is a `FileDialog` adapted for the editor (favorites, recent dirs, editor-settings sync; honours the `use_native_file_dialogs` editor setting, ignores `FileDialog.use_native_dialog`). Hidden by default; show with `popup_centered_clamped()` etc. `add_side_menu` was removed in 4.6; `disable_overwrite_warning` is deprecated in favour of `FileDialog.overwrite_warning_enabled`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorfiledialog.html)
- In 4.6 most members moved to the base `FileDialog` (`add_filter`, `add_option`, `filters`, `current_path`, `popup_file_dialog`, `access`, `file_mode`, signals). GDScript and C# source stay compatible; some C# **binaries** break for `access`, `display_mode`, `file_mode` and the `file_selected`/`files_selected`/`dir_selected`/`filename_filter_changed` signals (rebuild fixes it). **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/migrating/upgrading_to_godot_4.6.html)
- `FileDialog`: `FileMode` {OPEN_FILE, OPEN_FILES, OPEN_DIR, OPEN_ANY, SAVE_FILE(default)}; `Access` {RESOURCES (res://), USERDATA, FILESYSTEM}; `add_filter("*.png, *.jpg", "Images", mime)`; `filename_filter` (substring filter, user-editable); `root_subfolder`; signals `file_selected(path)`, `files_selected(paths)`, `dir_selected(dir)`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_filedialog.html)

## 3. Undo/redo and dirty state

### 3.1 EditorUndoRedoManager (editor-integrated)
- Holds one `UndoRedo` per edited scene plus a shared **global history** for things not tied to a scene (project settings, external resources). Get it with `EditorPlugin.GetUndoRedo()` or `EditorInterface.GetEditorUndoRedo()`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_editorundoredomanager.html)
- `create_action(name, merge_mode = MERGE_DISABLE, custom_context = null, backward_undo_ops = false, mark_unsaved = true)`; `add_do_method(object, method, ...)`, `add_undo_method(...)`, `add_do_property(object, property, value)`, `add_undo_property(...)`, `add_do_reference(object)`, `add_undo_reference(object)` (keeps freed nodes alive; "don't use for resources"), `commit_action(execute = true)`, `is_committing_action()`, `get_object_history_id(object)`, `get_history_undo_redo(id)` (advanced; positive ids = scene tabs, 0 = GLOBAL_HISTORY, -9 = REMOTE_HISTORY, -99 = INVALID_HISTORY), `force_fixed_history()`, `clear_history(id = INVALID_HISTORY, increase_version = true)`. Signals `history_changed`, `version_changed`. Unlike `UndoRedo`, operations take `(object, method name)` not a `Callable`. **VERIFIED** (same page)
- History selection (verified in `editor/editor_undo_redo_manager.cpp`): Node inside the edited scene -> that scene's history; **built-in** Resource (`res->is_built_in()`) -> the scene named by the path before `::`; **external resources (file-backed `.tres`) and any other object -> GLOBAL_HISTORY** (fallback). `custom_context` runs the same lookup on the context object and pins the pending action; mixing objects that resolve to different histories inside one action raises an error. The manager itself never calls `set_edited`; dirty tracking is version-based (`saved_version` vs current position, and each action's `mark_unsaved` flag) through `is_history_unsaved()` / `set_history_as_saved()`. **VERIFIED** (https://raw.githubusercontent.com/godotengine/godot/4.6/editor/editor_undo_redo_manager.cpp)
- Implication for a GDO tool editing file-backed resources: all its actions land in the global history; Ctrl+Z works while the editor focus is anywhere, and the editor's quit dialog will show "Save modified resources before closing?" when `is_history_unsaved(GLOBAL_HISTORY)` is true. **INFERRED** (from the code paths in 1.4 and this section).
- In C#, `AddDoMethod(GodotObject, StringName, params Variant[])` requires the target method to be callable through Godot's `Call`, i.e. a method the source generators expose (public method on a `partial` GodotObject-derived class) and snake_case/PascalCase as registered; lambdas cannot be used with the manager. **INFERRED** (from the API shape; the docs' C# basics page notes `Call`/`CallDeferred` expect the registered names).

### 3.2 Core UndoRedo (for a standalone tool)
- `UndoRedo` (any Control can own one): `create_action(name, merge_mode, backward_undo_ops)`, `add_do_method(Callable)` / `add_undo_method(Callable)` (Callables, so C# lambdas are fine), `add_do_property`/`add_undo_property`, `add_do_reference`/`add_undo_reference`, `commit_action(execute = true)`, `undo()`, `redo()`, `has_undo()`, `has_redo()`, `get_version()` (increases per committed action; compare to a saved version for dirty state), `clear_history(increase_version = true)`, `get_current_action_name()`, `max_steps` (0 = unlimited), signal `version_changed`. `MergeMode`: `MERGE_DISABLE`, `MERGE_ENDS` (keep first undo + last do; for sequential edits of one value), `MERGE_ALL`. Registration rule: register all do-ops together and all undo-ops together when operations depend on each other. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_undoredo.html)
- Engine details (`core/object/undo_redo.cpp`, 4.6): merging requires same action name, same `backward_undo_ops`, and **the previous action committed less than 800 ms ago** (`last_tick + 800 > ticks`); `start/end_force_keep_in_merge_ends()` protect ops from MERGE_ENDS pruning. When operations execute, `_process_operation_list` calls `res->set_edited(true)` on any `Resource` target under `TOOLS_ENABLED` (for both method and property ops). References are freed/unref'd when their history entries are discarded. **VERIFIED** (https://raw.githubusercontent.com/godotengine/godot/4.6/core/object/undo_redo.cpp)
- Consequence: even a private `UndoRedo` in a standalone tool marks resources `edited`, so the editor's `_save_external_resources` (triggered by any scene save) will write those `.tres` files to disk, possibly before the user pressed your "Save" button. Decide whether that is desired; if not, operate on in-memory duplicates and only `TakeOverPath`/save on explicit Save. **INFERRED** (from the two code facts above).
- The 800 ms merge window is a key UX detail for sliders/text fields: use `MERGE_ENDS` with a stable action name per field ("Edit Campaign.Title") to coalesce keystrokes. **INFERRED**

### 3.3 Resource dirty state and saving
- `ResourceSaver.Save(resource, path = "", flags = 0)`; empty path falls back to `resource_path`. Flags: `RELATIVE_PATHS`, `BUNDLE_RESOURCES`, `CHANGE_PATH` (update `resource_path` to the new location), `OMIT_EDITOR_PROPERTIES`, `SAVE_BIG_ENDIAN`, `COMPRESS` (binary only), `REPLACE_SUBRESOURCE_PATHS` (take over subresource paths). **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_resourcesaver.html)
- `Resource`: `resource_path` (setting it manually may fail if the path is cached; use `take_over_path(path)` so later loads return this instance), `resource_name`, `resource_local_to_scene`, `emit_changed()`/`changed` signal ("not emitted automatically for custom resource properties, so a setter must emit it"), `duplicate(deep)`, `duplicate_deep(mode)` (4.6: `DEEP_DUPLICATE_NONE/INTERNAL/ALL`; nested resources are duplicated only if local unless ALL), `generate_scene_unique_id()`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_resource.html)
- `EditorInterface.MarkSceneAsUnsaved()` marks only the current scene tab; `EditorUndoRedoManager.clear_history(id, increase_version = true)` marks a history unsaved without an undoable step. **VERIFIED** (class_editorinterface.html, class_editorundoredomanager.html)
- Nested sub-resources edited via a custom editor are a known pain: edits recorded only against the inner resource do not mark the file-backed parent as changed, so Ctrl+S does not write the file. Workarounds in the thread: add a no-op do/undo method on the parent (yields history-mismatch errors), route through a wrapper object, save manually in `_save_external_data` (duplicate saves, runs even on "Don't Save"), or keep the file-backed parent referenced in memory. The proposal is still open. **VERIFIED** (https://github.com/godotengine/godot-proposals/discussions/7168)
- A 4.6 forum report of a GraphEdit tool: `ResourceSaver.save()` returned OK but did not overwrite, `take_over_path` made it overwrite but with stale nested values; no confirmed resolution, pointers to the nested-resource proposal above. Treat nested `Resource` arrays with care (prefer making GDO children file-backed or ensuring every nested resource is `resource_local_to_scene = false` and saved with `FLAG_REPLACE_SUBRESOURCE_PATHS`). **VERIFIED** for the report (https://forum.godotengine.org/t/inconsistent-saving-resources-in-editor/133176); **INFERRED** for the mitigation.
- "Pending changes" UX used by other tools: Dialogic/Dialogue Manager style main-screen editors keep their own dirty flag, show it in their own UI, and implement `_get_unsaved_status`/`_save_external_data` so the editor's quit/close dialog includes them; the engine supports exactly this contract (1.4). **INFERRED** (contract verified; the addons' internals were not read line by line).

## 4. C# editor-tool pain points (assembly reload)

### 4.1 Mechanism and the tracking issue
- Godot loads the project assembly into a collectible `AssemblyLoadContext` in the editor (not when running games) and unloads/reloads it on every Build. If unloading fails you get ".NET: Failed to unload assemblies. Please check <this issue>" and **C# scripts stay unavailable until the editor restarts**. Tracker issue #78513 (opened June 2023) is still **open** as of Sep 2026 and applies to "any 4.x version". Listed causes: Newtonsoft.Json caches (not unload-friendly), System.Text.Json caches (needs clearing), generic C# script classes (#79519), default values on exported custom-resource properties (#80175), capturing variables in Callables (#81903, fixed in 4.3 via #83217), tool scripts whose init/dispose throws, `[GlobalClass]`/`[Tool]` scripts in general reported as the biggest risk by users; EF Core/SQLite. Editor setting `dotnet/project/assembly_reload_attempts` (default 3) is also the seconds to wait for unload. **VERIFIED** (https://github.com/godotengine/godot/issues/78513; setting from search summary of the editor settings doc — the exact doc page was not opened, so the setting detail is **INFERRED**)
- The 2023 engine fix "Fix editor integration breaking and causing error spam when reloading assemblies fails" made scripts from non-collectible assemblies not reload, GodotTools non-collectible, and stopped infinite retry; it is in 4.1+ so 4.6.2 has it. **INFERRED** (seen only via commit mirrors; PR number not confirmed).
- #102484 (TweenMethod/TweenCallback in tool scripts fails unload, repro 4.2-4.4) was fixed by PR #102837 "Skip serializing delegates with a disposed target", merged 2025-06-13, milestone 4.5 — so 4.6.2 includes it; delegates whose target was freed are dropped on reload. **VERIFIED** (https://github.com/godotengine/godot/issues/102484, https://github.com/godotengine/godot/pull/102837)
- #81903 (capturing a variable in a Callable prevents unloading) closed Apr 2024 via #83217 (milestone 4.3). **VERIFIED** (https://github.com/godotengine/godot/issues/81903)
- .NET rules behind all this: a collectible ALC unloads only when no thread has its methods on the stack and nothing outside holds strong references to its types/instances/assemblies: statics, strong GC handles, delegates/event handlers held by outer objects (the engine's delegate GCHandles are exactly this), reflection caches, `RegisteredWaitHandle`s, stack slots. `AssemblyLoadContext.Unloading` is the hook for cleanup. **VERIFIED** (https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)
- How reload works for plugin state (practitioner report, AssetPlacer C# plugin): on each rebuild Godot serializes plugin/tool-script state, reattaches scripts and restores it; plain C# objects in fields come back **null** (NullReference/ObjectDisposed until restart). Rules that worked for them: make helper classes `partial` GodotObject subclasses; keep fields Variant-compatible (Godot types, primitives, Godot collections); do not mark serialized fields `readonly`; use Godot signals instead of C# events/Actions; avoid captured variables in lambdas connected to signals (they do not reconnect after rebuild); stray statics caused similar errors. **VERIFIED** as a report (https://cookiebadger.itch.io/assetplacer/devlog/537327/godot-plugins-what-nobody-tells-you)
- Official C# docs: "State is currently not saved and restored when hot-reloading, with the exception of exported variables." **VERIFIED** (c_sharp_basics.html)
- Signals doc: lambdas that capture variables are not auto-disconnected when the receiver is freed (ObjectDisposedException); store the delegate and `-=` it in `_ExitTree`; `Callable.From` has the same problem; custom-signal `+=` subscriptions are not auto-disconnected either. **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_signals.html)
- `[Tool]` static state: static fields live in the collectible ALC; any static referencing an engine object or captured by the engine prevents unload, and all statics are lost on a successful reload. Treat statics in tool code as forbidden except for pure constants. **INFERRED** (from the .NET unloadability rules above and the #78513 reports).

### 4.2 Can a C# plugin be hot-reloaded in 4.4-4.6?
- Yes when the unload succeeds: Build -> unload -> reload -> plugin `_ExitTree`/`_EnterTree` effectively re-run with state restored from Variant-serializable fields. The docs' statement that editor plugins are "quite convoluted" is unchanged in 4.6. No 4.4/4.5/4.6 release note advertises a change to the reload mechanism; 4.4 raised the minimum to .NET 8, 4.5 fixed delegate serialization for freed targets and loads assemblies directly from APKs, 4.6 only changed `Tr()` parsing for C#. **VERIFIED** (https://godotengine.org/releases/4.4/, https://godotengine.org/releases/4.5/, https://godotengine.org/releases/4.6/, PR #102837); the "yes when it succeeds" summary is **INFERRED**.
- Real-world fixes that made C# plugins reload reliably:
  - YarnSpinner-Godot (C# EditorPlugin + import plugin): `[ModuleInitializer]` that subscribes to the assembly's `AssemblyLoadContext.Unloading` and clears its System.Text.Json cache; closed the issue in May 2025. **VERIFIED** (https://github.com/YarnSpinnerTool/YarnSpinner-Godot/issues/32)
  - ePlugin Framework (C# plugin framework, targets .NET 8, builds against 4.4.1/4.5.1/4.6.2/4.7.2): JSON reflection cache in the default context kept the assembly alive on every rebuild; fixed with an `AssemblyUnloadCleanup` registered first thing, clearing `JsonSerializerOptionsUpdateHandler.ClearCache` by reflection. Lessons: anything in the default context referencing your types blocks unload; register cleanup early; test with repeated rebuilds. **VERIFIED** (https://github.com/enaweg/godot-epluginframework, https://github.com/enaweg/godot-epluginframework/pull/32)
  - Cysharp/R3 plugin: cleanup from `_ExitTree` also run at the top of `_EnterTree` because `AddAutoloadSingleton` left stale state. **INFERRED** (search summary of https://github.com/Cysharp/R3/issues/125; not opened).
  - gdUnit4 (GDScript plugin shell + C# API assembly): duplicate script registration (`ScriptTypeBiMap.Add` "same key") on reload; fixed in their PR #344 (Feb 2024) but a user reported recurrence in Aug 2025. **VERIFIED** (https://github.com/godot-gdunit-labs/gdUnit4/issues/343)
  - One developer reported that moving `EditorPlugin` code from C# to GDScript made the error disappear. **INFERRED** (Mastodon post surfaced by search; page would not render for me).

### 4.3 What the community recommends (2025-2026), synthesized
- Keep the editor-side surface in C# small and "reload-clean": no statics with engine refs, no capturing lambdas on engine signals, no third-party serializers/reflection caches in tool code (or clear them in `AssemblyLoadContext.Unloading`), every `+=` mirrored by `-=` in `_ExitTree`, every added node freed in `_ExitTree`, every dock/inspector plugin removed. **INFERRED** (synthesis of 4.1-4.2 sources)
- Expect occasional editor restarts anyway; design the tool so a restart loses nothing (save early, keep an autosave/draft of unsaved GDO edits). **INFERRED**
- A GDScript shell for the EditorPlugin (plugin.cfg -> .gd) that instantiates C#-defined Resources and reads their exported properties is a valid, commonly used mitigation: GDScript can `load("res://X.cs").new()`, read/write C# properties by PascalCase name and call methods/connect signals; scripts cannot inherit across languages. C# resources must be `[GlobalClass]` to appear by name in pickers/type filters. **VERIFIED** for cross-language mechanics (https://docs.godotengine.org/en/4.6/tutorials/scripting/cross_language_scripting.html); **INFERRED** for the "[GlobalClass] needed for pickers" point (from the resource-picker source in 2.4).
- Dialogue Manager (GDScript addon) exposes a C# wrapper where game state is visible only through `[Export]` members and `[GlobalClass]` types; this is the pattern a GDScript shell + C# data would follow. **VERIFIED** (https://github.com/nathanhoad/godot_dialogue_manager/blob/main/docs/CSharp.md)

## 6. Export hygiene

- Export preset Resources tab: export modes (all resources / selected scenes / selected resources / all except checked / dedicated server), "Filters to export non-resource files", and "Filters to exclude files/folders" (e.g. `addons/contenido/*`). Files/folders whose name starts with `.` are never exported. **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/export/exporting_projects.html)
- `.gdignore` (empty file) makes Godot skip importing a folder, hides it from the FileSystem dock and makes its resources unloadable — not suitable for an addon the editor must load. **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/best_practices/project_organization.html)
- Feature tags: `editor` (editor build), `editor_hint` (editor build, running inside the editor), `editor_runtime` (editor build running the project), `template` (export-template build), `debug`, `release`, `pc`, `mobile`, `windows`, `android`; query with `OS.HasFeature()`. `Engine.IsEditorHint()` is the API for "code is running inside the editor". **VERIFIED** (https://docs.godotengine.org/en/4.6/tutorials/export/feature_tags.html, running_code_in_the_editor.html)
- **C# compilation facts (Godot.NET.Sdk 4.6):** configurations are `Debug`, `ExportDebug`, `ExportRelease`; `TOOLS` is added to `DefineConstants` **only when Configuration == Debug** (`<DefineConstants Condition=" '$(Configuration)' == 'Debug' ">$(DefineConstants);TOOLS</DefineConstants>`); `ExportDebug` adds `DEBUG`; platform constants `GODOT_WINDOWS;GODOT_PC`, `GODOT_ANDROID;GODOT_MOBILE` etc. come from `GodotTargetPlatform`; `GODOT` is always defined. **VERIFIED** (https://raw.githubusercontent.com/godotengine/godot/4.6/modules/mono/editor/Godot.NET.Sdk/Godot.NET.Sdk/Sdk/Sdk.props and .../Sdk.targets)
- The SDK does not exclude `addons/` and does not disable default compile globbing, so **every `.cs` under the project folder — including `addons/**` — is compiled into the single game assembly for export builds**; the export preset exclude filter only removes the files from the PCK, not from the DLL. Editor-only code therefore must be guarded with `#if TOOLS` (the pattern the official examples use) or removed from compilation with `<Compile Remove="addons/contenido/**" />` under a non-Debug condition, or placed in a separate project referenced only from a Debug-conditional `ProjectReference`. **VERIFIED** for the SDK facts; the three mitigation recipes are **INFERRED** (standard MSBuild; no official page documents them). A Godot 3 issue (#41196) confirms the failure mode when an `EditorPlugin` subclass ends up in an export compile. **INFERRED** (search summary only).
- Caveat with `#if TOOLS`: anything referenced from runtime code (e.g. a validation helper you also want at runtime) must live outside the guard; split "editor UI" (guarded) from "GDO model + validation rules" (unguarded, shipped). **INFERRED**
- `EditorExportPlugin` can additionally skip files programmatically during export if a filter is not enough. **INFERRED** (docs page not opened; mentioned in search results).

## 7. GraphEdit basics (for the later logic/graph task)

- `GraphEdit` provides the infinite grid, zoom, minimap, snapping and connection drawing, but **takes no action by default**: `connection_request`, `disconnection_request`, `delete_nodes_request`, `connection_to_empty`/`connection_from_empty`, `copy/cut/paste/duplicate_nodes_request`, `popup_request`, `node_selected/deselected`, `begin/end_node_move` are emitted and your code must implement each. Methods: `connect_node`/`disconnect_node`, `is_node_connected`, `get_connection_list_from_node`, `get_closest_connection_at_point`, `add_valid_connection_type`, `add_valid_left/right_disconnect_type`, `arrange_nodes`, `set_selected`, `get_menu_hbox` (toolbar; never free it), virtuals `_is_node_hover_valid`, `_get_connection_line`. Properties: `right_disconnects`, `snapping_enabled/distance`, `zoom/min/max/step`, `scroll_offset`, `minimap_*`, `show_grid`, `grid_pattern`, `connection_lines_curvature/thickness`, `connections` array. Docs strongly advise enabling low-processor usage mode; `get_children()` includes the internal `_connection_layer`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_graphedit.html)
- `GraphNode`: each child Control is a slot; `set_slot(idx, enableLeft, typeLeft, colorLeft, enableRight, typeRight, colorRight, iconL, iconR, drawStylebox)`, `set_slot_enabled_left/right`, `set_slot_type_*` (int types; negative blocks user connections; `ignore_invalid_connection_type`), `set_slot_color_*`, `set_slot_custom_icon_*`, `clear_slot`, `clear_all_slots`; **GraphEdit connections use port indices, not slot indices** (`get_input_port_slot(port)`, `get_output_port_slot(port)`, `get_input/output_port_count()`); `get_titlebar_hbox()` to add buttons; signals `slot_updated`, `slot_sizes_changed`; `title`, `slots_focus_mode`; `position_offset`, `resizable`, `selectable`, `draggable` come from `GraphElement`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_graphnode.html)
- Serialization pattern (no official tutorial exists): keep a plain data model (`GraphResource : Resource` with `Array<NodeData>` + `Array<EdgeData>` where each node has an id, type, `Vector2 PositionOffset`, payload) and treat GraphEdit purely as a view; rebuild the view from the model and route every user request through UndoRedo actions that mutate the model and re-sync the view. Reasons: GraphEdit emits requests rather than performing them, node names are the connection keys (`connect_node(fromName, fromPort, toName, toPort)`), and resource saving of nested sub-resources is the fragile part (see 3.3). **INFERRED** (from the API above and the 4.6 forum report)
- Known open 4.x issues worth planning around (open as of 2026-10-15): #123550 zoom/pan cost grows with node count; #117734 "Moving a GraphNode can't be undone" (you must record moves via `begin_node_move`/`end_node_move` yourself); #117620 GraphNode script binding breaks after copy-paste; #87492/#77739 `arrange_nodes` unusable/crashy on complex graphs; #98513 positions do not scale with editor scale; #88710/#119415/#54561 minimap gaps; #92120 disconnection UX; #63805 child order changes after moving nodes; #91857 `_connection_layer` in `get_children()`. **VERIFIED** (https://github.com/godotengine/godot/issues?q=is%3Aissue+is%3Aopen+GraphEdit+in%3Atitle)
- A 4.5 forum report: with `right_disconnects` the connection can only be dragged off the port side with the red dot. **INFERRED** (user report, not confirmed bug).

## 8. UX patterns from the editor (lists, search, split layouts, Tools menu)

- `Tree` is the editor's workhorse for searchable lists (Scene dock, FileSystem dock, Inspector sections): `columns`, `set_column_title`, `hide_root` (makes a flat list look multi-root), `SELECT_SINGLE/ROW/MULTI`, `item_selected`, `item_activated` (double-click/Enter), `button_clicked` (+ `TreeItem.add_button` for inline actions like "duplicate"/"delete"), `item_edited` (+ `TreeItem.set_editable` for inline rename), built-in incremental type-to-select (`allow_search`), drag-and-drop via `drop_mode_flags` and `get_drop_section_at_position`. **VERIFIED** (https://docs.godotengine.org/en/4.6/classes/class_tree.html)

The FileSystem dock, Scene dock, Inspector ("Filter Properties") and Project Settings all use this shape. **INFERRED** (observed editor behaviour; no doc page describes it)
- `ItemList` is the lighter choice for flat lists with icons (e.g. an asset gallery with `EditorResourcePreview` thumbnails, `icon_mode = ICON_MODE_TOP`). **INFERRED**
- Split layouts: `HSplitContainer` (list | editor) and nested `VSplitContainer` (editor / diagnostics), with `split_offset` persisted via the plugin's `_get_window_layout`/`_set_window_layout` (or `EditorDock._save_layout_to_config` for docks). The main-screen plugin's panel should be a Control set to Full Rect with vertical expand. **VERIFIED** for the layout hooks (class_editordock.html, making_main_screen_plugins.html); layout recommendation **INFERRED**.
- Editor icons/theme: `EditorInterface.GetEditorTheme().GetIcon("Search", "EditorIcons")` (the main-screen tutorial uses the same approach for the plugin icon); size everything by `GetEditorScale()`. **VERIFIED** (making_main_screen_plugins.html, class_editorinterface.html)
- Project > Tools entries (`add_tool_menu_item`) are the right place for one-off batch actions ("Validate all content", "Rebuild content index"), not for the main editor. 4.4 added `@export_tool_button` for GDScript (no C# attribute equivalent documented); in C# an inspector plugin `_ParseEnd` + `AddCustomControl(button)` gives the same "button in the inspector" affordance. **VERIFIED** (class_editorplugin.html; https://godotengine.org/releases/4.4/; https://matiaslavik.codeberg.page/godot-editor-scripting/)
- Diagnostics display: the editor's own pattern is a `RichTextLabel`/`Tree` with an icon column (`StatusError`, `StatusWarning` from EditorIcons) and double-click to jump to the offending object (`EditorInterface.InspectObject(obj, propertyName)` focuses the property). **INFERRED**

## Recommended architecture for the plugin

### Option A — Full C# plugin (main-screen `EditorPlugin` + `EditorInspectorPlugin` + `EditorUndoRedoManager`)
- Shape: `addons/contenido/ContenidoPlugin.cs` (`#if TOOLS`, `[Tool]`), a main-screen panel scene (list + editor + diagnostics), inspector plugin that handles GDO types and decorates/replaces properties (friendly labels via `add_property_editor(..., label:)`, pickers via `EditorResourcePicker` with `BaseType = "Texture2D"` / `"AudioStream"`), undo through `GetUndoRedo()` (global history for file-backed `.tres`), `_GetUnsavedStatus`/`_SaveExternalData` for close/quit integration, `_Build` to block Play on validation errors.
- Pros: one language, strongly typed access to GDO classes, full editor integration (Ctrl+Z, quit dialog, Inspector sub-editing, FileSystem drag-and-drop).
- Cons: every Build reloads the assembly; any leak = editor restart; plugin fields must be Variant-serializable; no lambdas on engine signals; adds friction to the whole team's build loop while the plugin is enabled. The docs still call C# plugins "quite convoluted".
- Mitigations: a `[ModuleInitializer]`-registered `AssemblyLoadContext.Unloading` cleanup; strict rules (no statics, named handlers with `-=`, free everything in `_ExitTree`); a rebuild-loop smoke test (build 10x with the screen open).

### Option B — GDScript shell + C# data (recommended default)
- Shape: `plugin.cfg` -> `contenido_plugin.gd` (main screen, docks, menus, undo/redo via `get_undo_redo()`, unsaved/save hooks, list/search UI, `EditorResourcePicker`s). The GDO model, validation rules and any heavy logic stay in C# `[GlobalClass]` Resources (shipped with the game, no `TOOLS` guard). The shell reads/writes GDO properties by PascalCase name, calls C# validators (`Call("Validate")` returning an `Array` of diagnostics) and uses `get_property_list()` on the C# resource to build generic forms; per-family forms are `.tscn`+`.gd` registered in a dictionary keyed by script class name (extension point). Optional: thin C# `EditorInspectorPlugin` only if the generic inspector decorations are wanted; it can be added later.
- Pros: the editor-side code hot-reloads without assembly unload (GDScript), no `TOOLS`-guard discipline for UI code, the assembly-reload problem shrinks to the C# resources themselves (plain data classes reload fine). Matches what gdUnit4, Dialogue Manager and several teams do.
- Cons: two languages in the repo; dynamic typing at the boundary (property names as strings; refactors in C# can silently break the shell — mitigate with a small contract test); cross-language inheritance is impossible, so validation helpers that the shell needs must be C# methods on the resources or a C# static utility invoked via a `GodotObject` wrapper.

### Option C — Standalone tool scene run from the editor (or as a separate "editor mode" of the game)
- Shape: a normal scene (`res://tools/contenido/Contenido.tscn`, C#) run with "Run Current Scene" or launched from Project > Tools; uses core `UndoRedo`, `FileDialog`, its own list/search UI, `ResourceSaver`/`ResourceLoader` directly; excluded from export by preset filter + `#if TOOLS` or a runtime `OS.HasFeature("editor")` gate.
- Pros: zero assembly-reload interaction (it runs in the editor-runtime process, not inside the editor), no editor API churn, debuggable with breakpoints, same code could later ship as an in-game mod editor.
- Cons: no Inspector/FileSystem integration (no drag-and-drop from the dock, no `EditorResourcePicker`, no editor undo history or quit dialog), must re-implement previews and pickers, and the editor's cached copy of a `.tres` can go stale until a filesystem scan (`EditorFileSystem.scan()` is not reachable from a separate process; the editor's own file watcher picks it up on focus). Validation diagnostics cannot block Play via `_Build`.

Recommendation: start with **B**; carry the GDO schema and validation in C# from day one so A or C remain possible. Revisit A only if the GDScript shell starts duplicating substantial C# logic.

### Top risks
1. **Assembly reload failures** (#78513 open, 4.x-wide) — any C# tool code leak costs an editor restart; even with B, `[GlobalClass]` resources with default-valued exported sub-resources or statics can trigger it. Budget a rebuild-loop test. **VERIFIED/INFERRED**
2. **Dirty-state semantics** — core `UndoRedo` and the editor manager both flip `Resource.set_edited(true)`, and the editor flushes edited external resources on any scene save; nested sub-resources may not be saved at all (proposal #7168 open). Decide early: file-backed GDO per entity vs nested, and whether the tool edits live resources or duplicates. **VERIFIED**
3. **Export leakage** — all `.cs` under the project compile into the game DLL; `#if TOOLS` is the only SDK-level switch; the export exclude filter only affects the PCK. A forgotten guard breaks export builds or ships editor code. **VERIFIED**
4. **4.6 API churn** — `EditorDock` is marked experimental; `add_control_to_dock`/bottom-panel APIs are deprecated; `EditorFileDialog` members moved in 4.6 (C# binary breaks). Pin to 4.6.x and isolate dock creation behind one function. **VERIFIED**
5. **GraphEdit later** — no built-in undo (node moves, #117734), perf degradation with node count (#123550), connections keyed by node names; design the data model first and keep GraphEdit as a view. **VERIFIED**
6. **Addon ecosystem is GDScript-first** — none of the candidate data editors has a C# API; LimboAI's C# path needs the module build. Plan C# interop through `[Export]`/`[GlobalClass]` surfaces only. **VERIFIED**
