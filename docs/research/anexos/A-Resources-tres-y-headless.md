## 1. Custom Resources in C# on Godot 4.x

### Registration and the Inspector / "Create New Resource" dialog
- **VERIFIED** `[GlobalClass]` registers the class by its type name; "The file name must match the class name in case-sensitive fashion"; global classes "show up in the Add Node and Create Resource dialogs"; an `[Export]` typed as a global class makes the Inspector accept "only instances of that global class or any derived classes"; `[Icon("res://...svg")]` only works together with `[GlobalClass]`; classes whose name starts with "Editor" are hidden from the Create dialogs. https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_global_classes.html
- **VERIFIED** If a subclass is *not* registered, the Inspector only restricts to the nearest built-in base type (e.g. `Resource`), so unregistered custom types give you no type safety in the editor. Same page.
- **VERIFIED** The docs' custom-resource C# example says "Make sure you provide a parameterless constructor." https://docs.godotengine.org/en/4.6/tutorials/scripting/resources.html
- **VERIFIED** "You need to (re)build the project assemblies whenever you want to see new exported variables or signals in the editor." Also needed for changes in tool scripts. https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_basics.html ; c_sharp_exports: "after building the current project it will be visible in the property editor."
- **INFERRED** GDScript's `class_name` needs no build step (the engine parses the script); the C# equivalent needs `dotnet build` plus the editor's assembly reload before the type appears. Consequence: every schema change on content types costs a build + reload cycle in the editor, and that reload is the fragile step described in section 6.

### What can be `[Export]`ed (nested Resources, collections, typed collections)
- **VERIFIED** "Exporting can only be done with Variant-compatible types." "Any type of Resource or Node can be exported." Enums and `[Flags]` enums export. C# arrays export "as long as the element type is a Variant-compatible type" (these map to Packed*Array: `int[]`, `float[]`, `string[]`, `Vector2[]`, `Color[]`, `byte[]`; "Other C# arrays are not supported by the Godot C# API since a packed array equivalent does not exist"). https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_exports.html ; https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_collections.html
- **VERIFIED** "only certain C# arrays and the collection types defined in the Godot.Collections namespace are Variant-compatible, therefore, only those types can be exported." `Godot.Collections.Array<T>` and `Godot.Collections.Dictionary<TKey,TValue>` give the editor a type hint (an `Array<ItemDef>` shows a typed array editor; typed dictionaries since 4.4). `System.Collections.Generic.List<T>`/`Dictionary<K,V>` cannot be exported (open proposal godot-proposals #10916 "Add Export support for System.Collections.Generic.List and Dictionary", 2024-10). Same pages; proposal found via `gh search issues --repo godotengine/godot-proposals`.
- **VERIFIED** Godot collections marshal every element on access: "Every operation on a Godot collection requires marshaling which can be expensive especially inside a loop"; "Using Godot collections is only recommended when absolutely necessary"; converting to a .NET collection copies every element. https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_collections.html
- **VERIFIED** Default values: "The default value of Godot arrays is null" (also dictionaries, C# arrays, strings). "Exporting works with fields and properties. They can have any access modifier." "A property's get is not actually executed to determine the default value" ("don't use complex properties"). c_sharp_exports page.
- **VERIFIED** `[Export]` requires a setter: diagnostic GD0103 "Exported member is read-only (no setter)"; GD0101 exported member must not be static; GD0102 unsupported type; GD0107 non-Node type exporting Node members; GD0401 class must derive from GodotObject; **GD0402 "Class must not be generic"**; GD0301/0302 generic type arguments must be Variant-compatible / `[MustBeVariant]`; GD0001 class must be `partial`. https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/diagnostics/index.html
- **INFERRED** from GD0103 + "parameterless constructor": `init`-only properties, positional `record` types and immutable domain objects cannot be the exported Godot-side definition. A `partial record class : Resource` is not a documented pattern; records' value-equality/`with` semantics clash with `GodotObject` reference identity. The Godot-side type must be a mutable `partial class` with public setters, which is exactly the shape the project's `src/domain` is trying to avoid.
- **VERIFIED** Generic custom Resources break the editor: #102057 (open, 2025-01) "Custom Resource extend from generic class display 'This inspector might be out of date. Please build the C# project'"; #110784 (open) same-named generic and non-generic classes cause assembly unload failure. https://github.com/godotengine/godot/issues/102057 ; https://github.com/godotengine/godot/issues/110784
- **VERIFIED** C# cannot `preload`; load is `GD.Load<T>()` / `ResourceLoader.Load<T>()` at runtime ("preload, as it works in GDScript, is not available in C#"). https://docs.godotengine.org/en/4.6/tutorials/scripting/c_sharp/c_sharp_differences.html
- **VERIFIED** `Callable` in C# is limited (no `bind/unbind`; custom callables from GDExtension unsupported). Same page. (Relevant only because the domain library must never receive one.)

### Known custom-Resource bugs that matter for a content pipeline (all topic:dotnet)
- **VERIFIED** #84470 (open, confirmed) "List of resources with default values erase data in certain circumstances (C#)": arrays of resources with initializers lose edited sub-properties on build unless the array itself changed. https://github.com/godotengine/godot/issues/84470
- **VERIFIED** #80175 (closed, fixed 4.3) `[Export] public MyResource Res { get; set; } = new();` used to error on build. Fixed, but shows that default-instantiating nested resources in field initializers has been fragile. https://github.com/godotengine/godot/issues/80175
- **VERIFIED** #81002 (open, "discussion") `ResourceLoader.Load<MyCustomResource>()` returns plain `Resource` in the editor context (tool code), giving InvalidCastException. https://github.com/godotengine/godot/issues/81002
- **VERIFIED** #119603 (open, repro on 4.6.2) exporting a custom Resource on a `[Tool]` script throws a casting error. https://github.com/godotengine/godot/issues/119603
- **VERIFIED** #84394 (open) `Changed` event on a custom `[Tool]` Resource does not reset properly on build. https://github.com/godotengine/godot/issues/84394
- **VERIFIED** #124477 (open, 2026-10-14) custom resource extending Shader cannot be loaded. (Shows the area still receives new bugs in the 4.7/4.8 timeframe.)

## 2. `.tres` text format, UIDs, `.res`, export pipeline

### Structure (format=3)
- **VERIFIED** Header: `[gd_resource type="ArrayMesh" format=3 uid="uid://dww8o7hsqrhx5"]` for resources, `[gd_scene format=3 uid="..."]` for scenes. `format=3` is Godot 4.x (`format=2` is 3.x). `load_steps` "is now deprecated and should be ignored if present" (4.6 stopped writing it: CHANGELOG 4.6 "Remove load_steps from resource_format_text.cpp" GH-103352). Sections in order: file descriptor, `[ext_resource ...]`, `[sub_resource ...]`, (`[node ...]`, `[connection ...]` for scenes) or `[resource]` for resources. "A resource that references another internal resource must appear after it." Sub-resources have no uid. External references are written `ExtResource("1_7bt6s")`, internal ones `SubResource("CapsuleShape3D_fdxgg")`. Values use constructor syntax (`Vector3(...)`, `Color(...)`, `PackedStringArray(...)`, `NodePath("...")`), arrays `[...]`, dictionaries `{ "k": v }`; `;` starts a comment that the editor discards; "Properties equal to their default values are not stored." The page gives no formal grammar and says the complete description is `resource_format_text.cpp` (`ResourceFormatLoaderText`). https://docs.godotengine.org/en/4.6/engine_details/file_formats/tscn.html
- **VERIFIED** `script_class="Name"` is written in the `[gd_resource ...]` header when the resource's script has a global name (`script->get_global_name()`), i.e. for `[GlobalClass]` C# types: `title += "script_class=\"" + String(script->get_global_name()) + "\" ";` and `ResourceLoaderText::recognize_script_class` reads it back. Source: scene/resources/resource_format_text.cpp (4.6 branch) lines ~1035-1038, 1162-1163, 1311-1343, 1789-1798. https://raw.githubusercontent.com/godotengine/godot/4.6/scene/resources/resource_format_text.cpp
- **VERIFIED** The script itself is an ext_resource: `[ext_resource type="Script" path="res://src/client/shell/GameShell.cs" id="1"]` (local project file; newer saves add `uid="uid://..."`). A custom-resource `.tres` therefore stores the **path (and uid) of the C# script** plus `script = ExtResource("...")` in `[resource]`; the docs warn: "Beware that resource files (*.tres/*.res) will store the path of the script they use in the file." https://docs.godotengine.org/en/4.6/tutorials/scripting/resources.html
- **VERIFIED** The format changed within the 4.x line (4.4 added uids to more references; 4.6 removed `load_steps` and added unique node IDs in scenes; "The changes are backwards-compatible and forwards-compatible", but re-saving produces "significant diffs"; use Project > Tools > Upgrade Project Files). https://docs.godotengine.org/en/4.6/tutorials/migrating/upgrading_to_godot_4.6.html
- **VERIFIED** Two format versions exist in the writer: `FORMAT_VERSION` and `FORMAT_VERSION_COMPAT` (`use_compat`), confirming the writer can emit a compat variant. resource_format_text.cpp line ~1798.

### Textures / audio references and `.import`
- **VERIFIED** Imported assets get a companion `<asset>.import` ("Make sure to commit these files"); the imported binary lives in `res://.godot/imported/` (not to be committed); `.tscn/.scn/.tres/.res` have no import options; reimport is triggered by MD5 change of the source. https://docs.godotengine.org/en/4.6/tutorials/assets_pipeline/import_process.html
- **VERIFIED** (local sample) a `.import` file holds `[remap] importer="texture" type="CompressedTexture2D" uid="uid://dkl2j6vv2y6dr" path="res://.godot/imported/canyon-v1.png-<md5>.ctex"` and `[deps] source_file=... dest_files=[...]`. So a `.tres` referencing a texture stores `[ext_resource type="Texture2D" uid="uid://..." path="res://assets/art/x.png" id="..."]` and the engine resolves the `.png` path through the `.import` remap to the `.ctex`.
- **VERIFIED** On export, the exporter reads each `.import`, writes a rewritten `.import` (only the `remap.path` for the selected platform features) and packs the `.godot/imported/...` file(s) it points to; the source `.png` itself is not what the game loads. editor/export/editor_export_platform.cpp (4.6) lines ~1379-1530. https://raw.githubusercontent.com/godotengine/godot/4.6/editor/export/editor_export_platform.cpp
- **VERIFIED** Headless caveat for CI: `--import` "Starts the editor, waits for any resources to be imported, and then quits. Implies --editor and --quit." https://docs.godotengine.org/en/4.6/tutorials/editor/command_line_tutorial.html  **INFERRED**: a fresh checkout has no `.godot/imported/`, so loading a `.tres`/scene that references textures fails until `--import` has run (community guides report exactly this).

### UIDs (`uid://`) and stability when moving files
- **VERIFIED** "Resource UIDs (Unique IDentifiers) allow the engine to keep references between resources intact, even if files are renamed or moved." Accessible via `uid://`. `ResourceUID` singleton: `create_id`, `add_id`, `set_id`, `text_to_id`, `id_to_text`, `path_to_uid`, `uid_to_path`, `ensure_path`; `INVALID_ID = -1`. https://docs.godotengine.org/en/4.6/classes/class_resourceuid.html
- **VERIFIED** Since 4.4: scripts and shaders (including `.cs`) get a sibling `*.uid` file (local project has e.g. `src/client/dice/DiceTray.cs.uid` containing `uid://cx8bso6awwl7l`); `.tres/.tscn` carry their uid in the header; imported assets carry it in `.import`. References in `ext_resource` store uid *and* path, the path "still being stored alongside for displaying in the editor UI" and "as a fallback if the UID reference becomes invalid"; falling back to path prints a warning and "should not be relied upon intentionally" (two resources could be swapped). Commit `*.uid` files; moving files outside the editor is a supported workflow if the `.uid` moves too (re-save dependents to clear warnings). https://godotengine.org/article/uid-changes-coming-to-godot-4-4/
- **VERIFIED** `ResourceSaver.save()` note: when the *project* (not the editor) is running, "any generated UID associated with the resource will not be saved" because that code only runs in editor mode. https://docs.godotengine.org/en/4.6/classes/class_resourcesaver.html  **INFERRED**: a runtime/headless exporter that writes `.tres` will not mint UIDs; only an editor (`--editor`/tool) context does.
- **VERIFIED** 4.6 fixed several uid edge cases (CHANGELOG 4.6: "Fix file duplication making random UID" GH-112015; "Fix the UID in the owner file changed when overwriting files in editor" GH-114499; "Don't assign a uid when copying resource file whose importer name is keep or skip" GH-112337; "Add reverse UID cache" GH-110464).

### ResourceSaver flags, `.res`
- **VERIFIED** `SaverFlags`: `FLAG_RELATIVE_PATHS`(1), `FLAG_BUNDLE_RESOURCES`(2) "Bundles external resources", `FLAG_CHANGE_PATH`(4), `FLAG_OMIT_EDITOR_PROPERTIES`(8) (drops `__editor`-prefixed metadata), `FLAG_SAVE_BIG_ENDIAN`(16), `FLAG_COMPRESS`(32) "Only available for binary resource types" (zstd), `FLAG_REPLACE_SUBRESOURCE_PATHS`(64). `save(resource, path="", flags=0)` picks a `ResourceFormatSaver` by extension. https://docs.godotengine.org/en/4.6/classes/class_resourcesaver.html
- **VERIFIED** "Users can save Resources as version-control-friendly text files (*.tres). Upon exporting a game, Godot serializes resource files as binary files (*.res) for increased speed and compression." https://docs.godotengine.org/en/4.6/tutorials/scripting/resources.html

### Export: "convert text resources to binary"
- **VERIFIED** `editor/export/convert_text_resources_to_binary` (bool, default **true**): "text resource (tres) and text scene (tscn) files are converted to their corresponding binary format on export. This decreases file sizes and speeds up loading slightly. Note: Because a resource's file extension may change in an exported project, it is heavily recommended to use load or ResourceLoader instead of FileAccess to load resources dynamically. Note: The project settings file (project.godot) will always be converted to binary on export, regardless of this setting." doc/classes/ProjectSettings.xml (4.6). https://raw.githubusercontent.com/godotengine/godot/4.6/doc/classes/ProjectSettings.xml
- **VERIFIED** Mechanism: for every `.tres`/`.tscn`, `force_binary = convert_text_to_binary && (tres||tscn)`; `_export_customize` loads the resource, saves it as `<basename>.res` (scenes `.scn`: "TSCN PackedScene representation is inefficient, so repacking is also desired") under `.godot/exported/<hash>/`, and the exporter adds a **path remap** (`path_remaps.push_back(path); path_remaps.push_back(export_path);`) so `ResourceLoader.Load("res://x.tres")` still resolves in the exported build. editor_export_platform.cpp lines 870-990, 1337, 1564-1570. **INFERRED**: `FileAccess`/`DirAccess` based scanning of `*.tres` breaks in exports; `ResourceLoader.list_directory()` (4.4+) returns "the original file names as visible in the editor before exporting" but "The order of files and directories returned by this method is not deterministic". https://docs.godotengine.org/en/4.6/classes/class_resourceloader.html
- **VERIFIED** `.cs` files are replaced by a single newline on export unless `dotnet/include_scripts_content` is on; the compiled assembly is what ships. modules/mono/editor/GodotTools/GodotTools/Export/ExportPlugin.cs (4.6).

## 3. Shared-resource mutation pitfalls

- **VERIFIED** "The engine keeps a global cache of all loaded resources, referenced by paths"; "A resource will be cached when loaded for the first time and removed from cache once all references are released"; subsequent loads of the same path return the same instance. "Keep in mind that loading a resource fetches the cached resource instance maintained by the engine. To get a new object, one must duplicate an existing reference or instantiate one from scratch with new()." https://docs.godotengine.org/en/4.6/classes/class_resource.html ; https://docs.godotengine.org/en/4.6/tutorials/best_practices/godot_interfaces.html
- **VERIFIED** `resource_local_to_scene` (default false): "If true, the resource is duplicated for each instance of all scenes using it", so one scene instance can modify it without affecting others; "Changing this property at run-time has no effect on already created duplicate resources." **INFERRED** from the `duplicate` semantics below: it applies to the resource it is set on; nested resources are not automatically covered. "Fix Unique Resources from Inherited Scenes" landed in 4.6.1 (GH-115862).
- **VERIFIED** `duplicate(deep=false)`: shallow, nested arrays/dictionaries/resources are **shared** with the original. `duplicate(true)`: arrays, dictionaries and packed arrays are copied recursively, but **nested Resources are copied only if they are "local"** (no path / scene-local path); properties flagged always/never-duplicate override this. "Fails for custom resources whose _init() has required parameters." https://docs.godotengine.org/en/4.6/classes/class_resource.html
- **VERIFIED** 4.5 added `duplicate_deep(DeepDuplicateMode)`: `DEEP_DUPLICATE_NONE` (collections copied, subresources still shared), `DEEP_DUPLICATE_INTERNAL` (only path-less / scene-local subresources copied), `DEEP_DUPLICATE_ALL` (every subresource copied even with a non-local path). The 4.5 notes say the old behaviour "does not duplicate subresources stored inside Array or Dictionary properties" and the new methods "give users full control over what gets duplicated or not". https://godotengine.org/releases/4.5/ ; Resource class page. 4.6 added a `DUPLICATE_INTERNAL_STATE` flag (CHANGELOG 4.6 GH-57121).
- **VERIFIED** `ResourceLoader.CacheMode`: `CACHE_MODE_IGNORE`(0) main resource and its subresources bypass the cache (dependencies still REUSE); `CACHE_MODE_REUSE`(1) default; `CACHE_MODE_REPLACE`(2) refresh already-cached instances in place from disk; `CACHE_MODE_IGNORE_DEEP`(3) and `CACHE_MODE_REPLACE_DEEP`(4) propagate through external dependencies. `has_cached(path)`; `take_over_path()` can override a cache entry. https://docs.godotengine.org/en/4.6/classes/class_resourceloader.html
- **VERIFIED** The `Changed` signal is not emitted automatically for custom resources: call `EmitChanged()` in setters; tool nodes must connect/disconnect `Changed` when the resource is swapped. https://docs.godotengine.org/en/4.6/tutorials/plugins/running_code_in_the_editor.html
- **Read-only / immutable definitions.** **VERIFIED** Godot has no immutable-Resource concept; only `Godot.Collections.Array/Dictionary.MakeReadOnly()`/`IsReadOnly` exist (collections page mapping of `make_read_only`). **INFERRED** patterns: (a) treat the loaded Resource as a read-only *authoring* object and map it once into immutable domain records (the project's current design); (b) `Duplicate(true)` / `DuplicateDeep(DeepDuplicateMode.All)` before any runtime mutation; (c) `MakeReadOnly()` on exported collections after load. Any mutation of a cached definition silently leaks into every other user of that path and, in a `[Tool]` context, can be *saved back to disk* ("Modifications made in the editor are permanent, with no undo/redo").

## 4. Headless Godot with a .NET project

### What the CLI offers
- **VERIFIED** `--headless` = `--display-driver headless --audio-driver Dummy`, "Useful for servers and with --script"; required on CI without GPU. `-s/--script <script>`: "The script must inherit from SceneTree or MainLoop" (the docs example is `.gd`; the page never says GDScript-only). `--check-only` parses and quits. `--main-loop <name>`: "Run a MainLoop specified by its global class name." `--`/`++`: following args readable via `OS.GetCmdlineUserArgs()`. `--quit`, `--quit-after N`, `--import`, `--build-solutions` ("Build the scripting solutions (e.g. for C# projects). Implies --editor and requires a valid project to edit."), `--export-release <preset> <path>` / `--export-debug` / `--export-pack` (editor binary required; export templates installed; output path relative to project.godot). `--path`, `--scene`, `--script` are "Only available in editor builds, and export templates compiled with disable_path_overrides=false". https://docs.godotengine.org/en/4.6/tutorials/editor/command_line_tutorial.html
- **VERIFIED** (engine source, language-agnostic) `-s` does `ResourceLoader::load(script)`, then `script_res->can_instantiate()`, `ClassDB::instantiate(script_res->get_instance_base_type())`, `cast_to<MainLoop>`, `set_script`. `--main-loop X` resolves `X` through `ScriptServer::is_global_class`, so it works with any language that registers global classes. main/main.cpp (4.6) lines ~4265-4320. https://raw.githubusercontent.com/godotengine/godot/4.6/main/main.cpp
- **VERIFIED** MainLoop docs show a C# `CustomMainLoop` example and say a MainLoop script can be "provided from the command line (with e.g. godot -s my_loop.gd)" or via `application/run/main_loop_type`. https://docs.godotengine.org/en/4.6/classes/class_mainloop.html
- **INFERRED** (from the above + next subsection): `godot --headless --path . -s res://tools/ExportCatalog.cs` or `--main-loop ExportCatalog` with a `[GlobalClass] partial class ExportCatalog : SceneTree` **should** work *provided the project assembly is already built*, because `CSharpScript::can_instantiate()` fails with "Cannot instantiate C# script because the associated class could not be found" if the class is not in the loaded assembly (csharp_script.cpp 4.6 lines ~2349-2360). No official C# `-s` example exists; this needs a short spike. The safer, widely used pattern is a **main scene / autoload Node** that checks `OS.GetCmdlineUserArgs()` and quits (this is how Chickensoft GoDotTest runs: `godot --run-tests --quit-on-finish`, a Node in the main scene calls `GoTest.RunTests` from `_Ready`). https://github.com/chickensoft-games/GoDotTest

### Does it need the editor build, and `dotnet build` first?
- **VERIFIED** The editor (TOOLS_ENABLED) binary loads the project assembly from `res://.godot/mono/temp/bin/Debug/<AssemblyName>.dll` at startup via `_try_load_project_assembly()`; if the file does not exist it silently continues ("it may just happen to be it wasn't built yet"; the error prints only with `--verbose`). Nothing in the runtime path triggers a build. Export-template builds instead load from the `data_<app>_<platform>_<arch>` publish directory (or the pck `.godot/mono/publish/<arch>` on Android). modules/mono/mono_gd/gd_mono.cpp (4.6) lines ~711-765; modules/mono/godotsharp_dirs.cpp lines 47-59, 142, 171-212. https://raw.githubusercontent.com/godotengine/godot/4.6/modules/mono/mono_gd/gd_mono.cpp ; https://raw.githubusercontent.com/godotengine/godot/4.6/modules/mono/godotsharp_dirs.cpp
- **INFERRED** therefore: for a headless data-export run you need (1) the **.NET editor binary** (`Godot_v4.6.2-stable_mono_win64.exe`), (2) a prior `dotnet build` (Debug configuration, because the editor binary expects `temp/bin/Debug`), or `godot --headless --build-solutions --quit` which implies `--editor`, and (3) `--import` once per fresh checkout if any texture/audio is referenced. The Godot.NET.Sdk output path is fixed to `.godot\mono\temp\bin\<Configuration>\` (Sdk.props lines 20-30), so a plain `dotnet build` from the solution root lands in the right place.
- **VERIFIED** `.NET SDK` discovery at export time is a known CI pain: forum reports of `--headless --export-release` failing with "Can't find .NET SDK" on 4.4 mono until `DOTNET_ROOT`/`PATH` was set. https://forum.godotengine.org/t/problem-exporting-c-project-from-command-line-cant-find-net-sdk/113124 (community, not official). The engine resolves `hostfxr` via `hostfxr_resolver` and then falls back to `dotnet` on `PATH` (gd_mono.cpp `find_hostfxr`).
- **VERIFIED** Community CI pattern (Chickensoft setup-godot): `actions/setup-dotnet` then `dotnet restore` then `chickensoft-games/setup-godot@v2` with `use-dotnet: true, include-templates: true` then `godot --headless --build-solutions --quit || exit 0` then `dotnet build --configuration Release`. The `|| exit 0` is undocumented (the build-solutions step can return non-zero even on success). https://github.com/chickensoft-games/setup-godot

## 5. Reading `.tres` from plain .NET without Godot

- **VERIFIED** The format is documented only informally (section 2); the docs page points to `resource_format_text.cpp` as the real spec, and the writer has a `FORMAT_VERSION_COMPAT` path, so the format is engine-owned and has changed in 4.4 (uids everywhere) and 4.6 (`load_steps` removed, node unique IDs). https://docs.godotengine.org/en/4.6/engine_details/file_formats/tscn.html
- **VERIFIED** Existing parsers. .NET: `Righthand.GodotTscnParser` (NuGet, ANTLR-based, alpha, **.tscn only**; the author says the aim is source generators "since the format isn't well documented"; targets net5-net7). https://www.nuget.org/packages/Righthand.GodotTscnParser/1.0.0-alpha9 . Python: `godot_parser` (stevearc) handles both `.tscn` and `.tres` with a low-level API, a good reference implementation. https://github.com/stevearc/godot_parser . Rust: `gdscript-scene` crate parses `.tscn/.tres` with byte spans. https://docs.rs/gdscript-scene . No maintained .NET `.tres` reader was found.
- **INFERRED** Writing a small .NET reader is feasible for a *constrained* subset (your own `[GlobalClass]` resources with scalars, strings, enums, `Array<T>`/`Dictionary` and `ExtResource`/`SubResource` references): INI-like section headers with `key="value"` attributes, `key = <Variant literal>` lines, and a Variant literal grammar (numbers, strings with escapes, `true/false`, `null`, `Type(...)` constructors, `[...]`, `{...}`). Risks:
  1. **Type reconstruction**: `script_class` names the C# class only for the top resource; sub-resources of custom type are `[sub_resource type="Resource" script=ExtResource("...")]`, so the parser must map script *paths/uids* to domain types.
  2. **Defaults are omitted** ("Properties equal to their default values are not stored"): the reader must know the C# default of every property; a default changed in C# silently changes old files' meaning.
  3. **Ordering / ids**: `sub_resource` ids are editor-generated strings (`generate_scene_unique_id`), can collide across saves, and must be declared before use; ext ids like `1_7bt6s` are also regenerated on save.
  4. **UID vs path**: references carry both; the editor resolves by uid first. A plain reader has no UID database unless it indexes `*.uid`, `.import` and resource headers itself (`.godot/uid_cache.bin` is a cache, not source).
  5. **Variant literal surface**: `Vector2(...)`, `Color(...)`, `PackedStringArray(...)`, typed-array literals for typed exports, `StringName(&"x")`, `NodePath("...")`, escape sequences; plus format drift (4.4/4.6 header changes already happened).
  6. Textures/audio referenced from content are `.import`-remapped files that a .NET reader cannot load anyway; the domain only needs the *path/uid*, which is fine.
- **Alternative (recommended by the evidence)**: have Godot (headless, editor binary, after `dotnet build`) load the `.tres` graph with the real loader and emit a **neutral catalog** (JSON via a System.Text.Json source-generated context, or a binary pack) plus a **content hash** (e.g. SHA-256 over the sorted `.tres` bytes + the exporter's version string) stored next to the catalog. CLI tools and xUnit tests read the catalog; one test asserts `hash(catalog) == hash(sources)` to detect staleness and tells you to re-run the exporter. This reuses the only authoritative parser and keeps `src/domain` Godot-free. The cost: the catalog becomes a build artifact (commit it or generate it in CI before tests), and the exporter is a Godot-side tool with the headless caveats of section 4.

## 6. C# editor stability: assembly reload / unload

- **VERIFIED** Tracker #78513 ".NET: Failed to unload assemblies" is **open** (created 2023-06-21, last activity 2026-09-22, 194 comments, affects "Any 4.x version"). "After unloading has failed, C# scripts will be unavailable until the editor is restarted." Causes: libraries incompatible with collectible AssemblyLoadContexts (Newtonsoft.Json issue 2414, dotnet/runtime 65323, EF Core/SQLite reported in 2026), strong GCHandles, static references, events/delegates kept alive; the recommended mitigation is cleanup registered on `AssemblyLoadContext.Unloading`. https://github.com/godotengine/godot/issues/78513
- **VERIFIED** Engine-side behaviour (4.6 source): on reload the editor calls `UnloadProjectPluginCallback`; on failure prints "Failed to unload assemblies. Please check https://github.com/godotengine/godot/issues/78513" and, after `dotnet/project/assembly_reload_attempts` (default 3; "Effectively also the timeout in seconds to wait for unloading of script assemblies to finish") failures, prints "Giving up on assembly reloading. Please restart the editor if unloading was failing." gd_mono.cpp lines ~768-810; ProjectSettings.xml.
- **VERIFIED** Reload-related churn in the 4.6 line itself: 4.6.0 "Improve performance of CSharpLanguage::reload_assemblies" (GH-106299) and "Remove EFS update on reloading assemblies" (GH-108487); **4.6.1 reverted** GH-106299 (GH-115759); **4.6.2 re-reverted** GH-108487 "but with deferred call" (GH-117617). The reload path was patched in every 4.6.x point release. CHANGELOG 4.6.x C# sections.
- **VERIFIED** Open 4.5/4.6-era issues in this area: #110608 (open, 4.5) `ScriptTypeBiMap` "add existed key" error spam on build; #111881 (closed) duplicate-key exception in `ScriptTypeBiMap` 4.5; #110971 (closed) 4.5 build log spam; #117143 (open, 4.6.1) a C# EditorPlugin dock is already disposed when the ALC `Unloading` event fires, so a plugin cannot remove its dock cleanly; #86244 (open) C# `EditorInspectorPlugin` throws when connected to `Resource.Changed`; #114860 (open, 2026-01) `PropertyListChanged` emitted after disposal in a C# tool script; #102484 (closed) `TweenMethod/TweenCallback` in tool scripts blocked unloading. Found via `gh search issues --repo godotengine/godot`.
- **VERIFIED** `@tool`/`[Tool]` inspector bug GH-66381 "Inspector not running code in @tool scripts until restart" is still **open with milestone 4.8**; the 4.6 docs say "You may need to restart the editor. This is a known bug found in all Godot 4 versions". https://github.com/godotengine/godot/issues/66381 ; https://docs.godotengine.org/en/4.6/tutorials/plugins/running_code_in_the_editor.html
- **VERIFIED** C# `EditorScript`s cannot be run from the script editor ("it only supports GDScript"); C# tool scripts appear in the command palette only with `[GlobalClass]`. Same page. The basics page: "Writing editor plugins is possible, but it is currently quite convoluted."
- **Does this affect custom Resources?** **VERIFIED/INFERRED**: plain `[GlobalClass] partial class X : Resource` without `[Tool]` is the least exposed case; the editor only needs its property list (requires a build to refresh). Once you add `[Tool]` (needed for setters/validation/`EmitChanged` in the editor, GH-66381 notwithstanding), an `EditorPlugin`, an `EditorInspectorPlugin`, or any third-party library inside the Godot assembly (JSON libs, EF/SQLite, DI containers with statics), you enter the #78513 failure class and pay restart cycles. Godot-proposal #9001 "Make the C# tool script reloading process easier to work with" is open. Mitigations: keep the Godot assembly thin (no heavy NuGet deps in the main csproj; the domain/application libs referenced by it are also loaded in the collectible ALC, so their statics/events count too), register `AssemblyLoadContext.Unloading` cleanup, avoid static caches of Godot objects, keep `assembly_reload_attempts` default, and accept editor restarts.

## Implications for the decision: `.tres` as canonical source vs neutral JSON edited by a Godot plugin

### Option A: `.tres` (custom `[GlobalClass]` Resources) is canonical
Pros
- Native Inspector editing with typed pickers, sub-resource nesting, drag-and-drop of textures/audio/scenes, `uid://` references that survive renames (VERIFIED sections 1-2).
- The export pipeline is free: `.tres` to `.res` conversion and path remaps are automatic; `.import` handling is automatic.
- Godot does the referential integrity (missing ext_resource warnings, uid fallback).
Cons
- The Godot-side definition type must be a mutable `partial class : Resource` with public setters, parameterless ctor, Godot.Collections only, no generics, no records/init-only (VERIFIED GD0103/GD0402, docs). You end up with **two type systems** (Resource authoring classes + immutable domain records) and a hand-written mapping layer; that mapping is where the "never leak Resource/Node/Callable into domain" rule is enforced.
- Plain .NET tools/tests cannot read `.tres` without either a home-grown parser (undocumented, engine-owned, drifted in 4.4 and 4.6, defaults omitted, uid/path duality) or a Godot-headless export step (needs the .NET editor binary, `dotnet build` first, `--import` on fresh checkouts, seconds of startup, SDK-discovery issues on CI).
- Editor authoring of custom Resources in C# sits on the fragile assembly-reload path (#78513 open since 2023, patched in each 4.6.x), tool-script inspector bug GH-66381 (milestone 4.8), and several open custom-Resource C# bugs (#84470 data loss in arrays of resources, #81002, #119603, #102057).
- Every schema change = rebuild + reload (and sometimes restart) before the Inspector shows it.
- Shared-instance mutation hazards (cache, `duplicate` nuances) only matter if runtime code touches Resources; mapping to immutable domain records at load neutralises them.

### Option B: neutral JSON (schema-validated) is canonical; a Godot `EditorPlugin` edits it
Pros
- Domain, CLI tools and xUnit read the same file with System.Text.Json source generation (AOT-safe on iOS, VERIFIED MS docs); no Godot binary in the unit-test loop; schema in git; diffs are stable and independent of Godot format changes.
- The domain model can stay immutable records; no second type system.
Cons
- You write and maintain the editor UI yourself (C# `EditorPlugin`/`EditorInspectorPlugin` in Godot is "quite convoluted" per the docs, hits the same reload/unload fragility, arguably *more* than passive Resources, and has open dock/inspector-plugin bugs #117143, #86244). Alternative: edit JSON outside Godot (any editor + schema) and keep the plugin minimal (validation, preview, asset-path pickers).
- Asset references (textures/audio) are plain paths/uids in JSON; renames in the FileSystem dock will not update them. You need a uid-based convention (store `uid://` strings and resolve with `ResourceUID`/`ResourceLoader` at runtime) or a validator that runs under Godot headless.
- No automatic `.tres` to `.res` optimisation; JSON must be included via export filters (`*.json` non-resource include filter) and parsed at runtime (fine for a content catalog of this size, INFERRED).

### Hybrid worth considering
Keep JSON canonical for *data* (campaign/actor/item definitions) and use `.tres`/scenes only for *presentation bindings* (which texture/scene/sound an id maps to), referenced by uid; a Godot-headless validator (main-scene + `--` args, after `dotnet build`) checks that every uid in JSON resolves. This keeps the domain Godot-free, uses Godot where it is strong (asset references), and never requires parsing `.tres` from .NET.

### Top 5 risks (ranked)
1. **Parsing `.tres` outside Godot**: undocumented, engine-owned format that already changed in 4.4 and 4.6; omitted defaults and script-path/uid typing make a home-grown reader a silent-corruption risk. (VERIFIED format facts; INFERRED severity.)
2. **C# editor reload/unload fragility**: #78513 open; 4.6.1 and 4.6.2 each shipped reverts in the reload path; tool scripts/plugins/inspector plugins amplify it. Affects both options, more so the plugin-heavy Option B and `[Tool]` Resources in Option A.
3. **Dual type systems and mutable Godot-side definitions** (Option A): exported members need setters and Godot collections; mapping to immutable domain types is manual and must be kept in sync with every content type.
4. **Headless C# pipeline on CI**: editor binary + `dotnet build` + `--import` + export templates + .NET SDK discovery; a `-s`/`--main-loop` C# entry is plausible but unverified by any official example; long-running headless C# has an open crash (#124441).
5. **Mobile/AOT drift**: iOS is NativeAOT-only with a reflection-dependent bootstrap (#115715) and open AOT/iOS crashes (#96072, #124016, #116165); 4.8 raises the TFM floor to net10.0. Any reflection-based serialization (JSON or otherwise) in the domain must be source-generated now.
